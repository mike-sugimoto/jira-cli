## 1. ビジョン

### 課題

部内のエンジニアは実装やバグ修正に Claude Code を使っていますが、Claude Code は Jira を読めません。そのため現在は、チケットの内容やチケットの一覧をブラウザからコピーし、手作業でチャットに貼り付けています。これがチケットや一覧のたびに繰り返され、Claude Code に作業を任せる流れが途切れてしまいます。

Jira MCP サーバーは選択肢になりません。会社の方針とコストの面で使えないうえ、権限の範囲が広く、誤って Jira に書き込んでしまう懸念が現実にあるからです。

### ビジョン

ループエンジニアリングを加速します。エンジニアがチャットで Claude Code にチケットの作業を頼むと、Claude Code は必要な情報を自分で Jira から読み、レビュー可能なプルリクエストまで作業を進めます。

jira-cli は、それを可能にする小さく信頼できる橋渡しです。**設計上、読み取り専用**で、**特定のプロジェクトに限定できる**ため、エンジニアも組織も、何かを変更されることを心配せずに自律エージェントへ渡せます。

### 製品の形

- Claude Code がシェルから呼び出すコマンドラインツール。
- Claude Code が動く場所で動く：WSL や Docker コンテナ（Linux）の中、および Windows。
- 部内で公開し、各エンジニアが自分でインストールして、自分の Jira Cloud の認証情報で使う。
- 1つの設定で接続する Jira Cloud サイトは1つ。

## 2. 用語集

- **チケット（Ticket）** — 種類を問わない Jira の課題（バグ、ストーリー、タスク、サブタスク、エピック）。
- **エージェント（Agent）** — jira-cli を呼び出す Claude Code。
- **許可プロジェクト（Allowed projects）** — jira-cli が読んでよい Jira プロジェクト。ユーザー設定ファイルに列挙する。
- **ユーザー設定ファイル（User configuration file）** — Jira サイト、認証情報、許可プロジェクト、一覧の既定件数などの設定を持つファイル。エージェントではなくエンジニアが管理する。
- **関連チケット（Related ticket）** — 別のチケットから、親、サブタスク、子、または課題リンクをたどって到達するチケット。
- **ループ（Loop）** — §3 で説明する、依頼からマージ済みの PR までの作業の流れ。

## 3. jira-cli が支えるループ

目指す作業の流れの全体です。jira-cli が担うのは **（jira-cli）** の付いた手順だけで、残りは Claude Code、git、エンジニアが担います。

1. エンジニアが Claude Code に未解決のチケットを見せるよう頼む。Claude Code が一覧を表示する **（jira-cli）**。
2. エンジニアが1つを選ぶ。Claude Code がチケットの全体、関連チケット、添付ファイル、変更履歴を読む **（jira-cli）**。
3. Claude Code が、必要な確認の質問をエンジニアにする。
4. Claude Code が変更を実装し、プルリクエストを作る。
5. マージ後、Claude Code が Jira チケットに書く文章（原因、対策）の下書きを作る。必要ならチケットを読み直す **（jira-cli）**。エンジニアがそれを手作業で Jira に貼り付け、タスクは完了する。

Jira への変更（担当者の設定、ステータスの遷移、コメント）はすべて手作業のままです。

## 4. 機能と機能要件

### F1. チケット一覧

- **FR-1** 明示的に指定した1つ以上の許可プロジェクトのチケットを一覧表示する。プロジェクトの指定が無いリクエスト、または許可されていないプロジェクトを1つでも含むリクエストは拒否し、エラーで許可プロジェクトを示す。さらに、担当者（「自分」を含む）、ステータス、課題タイプ、優先度、スプリント、ラベルを任意に組み合わせて絞り込める。ステータスで絞り込まない場合は、未解決のチケットが対象になる。結果は更新日時の新しい順に並べる。
- **FR-2** 結果は件数を限定して返し、多い場合はページ送りできる。既定のページ件数はユーザー設定ファイルで決める（初期値 20）。1回のリクエストは上限（初期値 100）を超えられない。
- **FR-3** 一覧の各項目には、チケットを選ぶのに十分な情報を表示する：キー、課題タイプ、サマリー、ステータス、優先度、担当者、最終更新日時。

### F2. チケットの全体情報

- **FR-4** キーを指定して1つのチケットを取得し、実装に必要な情報をすべて返す：サマリー、説明、課題タイプ、ステータス、優先度、ラベル、コンポーネント、修正バージョン、報告者、担当者、作成日時と更新日時、時系列順のすべてのコメント。
- **FR-5** リッチテキスト（説明、コメント）は、構造を保った読みやすいプレーンテキストで表示する：見出し、リスト、コードブロック、表、リンク、メンション。
- **FR-6** 値が入っているカスタムフィールドを、表示名とともに含める。ツールが安全に表示できない形の値は省略する。ただし、エンジニアがユーザー設定ファイルでそのフィールドを指定した場合は、構造化データのまま出力する。

### F3. 関連チケット

- **FR-7** 種類を問わずチケットの親またはエピック、子（サブタスクとエピック配下のチケット）、リンクしたチケットをリンクの種類（例：「blocks」「duplicates」）とともに表示する。子が許可されていないプロジェクトにある場合も結果は成功とし、その子はキーだけを表示して、エンジニアがそのプロジェクトを許可プロジェクトに追加できることを伝える。
- **FR-8** 関連チケットは自動ではなく要求に応じて取得する。エージェントが必要な深さだけを取得できるようにするため。

### F4. 添付ファイル

- **FR-9** チケットの添付ファイルを一覧表示する：ファイル名、サイズ、種類、作成者、日時。
- **FR-10** 選んだ添付ファイル、またはすべての添付ファイルを、ツールが管理するチケットごとのフォルダにダウンロードし、各ファイルの保存場所を報告する。そのフォルダに既にあるファイルは、新しいダウンロードで置き換える。

### F5. 変更履歴

- **FR-11** チケットの変更履歴を表示する：誰が、どのフィールドを、何から何に、いつ変更したか。ツールが安全に表示できないフィールドでは、変更前と変更後の値を省略する。

### F6. アクセス制御

- **FR-12** アクセスはユーザー設定ファイルに列挙した許可プロジェクトに限る。jira-cli はこのファイルを、どのプロジェクトのワークスペースにも含まれない、固定のユーザー単位の場所からだけ読む。README には、場所、すべての設定項目、エージェントによる変更からファイルを守る方法を書く。
- **FR-13** 許可プロジェクト以外のチケットや一覧へのリクエストは、分かりやすいエラーで拒否する。他のプロジェクトにある関連チケットはキーだけを表示し、アクセス不可と示す。その内容は一切取得しない。
- **FR-14** コマンドラインのオプションや環境変数で、許可プロジェクトを広げたり、別の設定ファイルを指定したりはできない。
- **FR-15** 認証情報にどの権限があっても、jira-cli は Jira に書き込みのリクエストを一切送らない。

### F7. 認証

- **FR-16** エンジニア自身の認証情報（アカウントのメールアドレスと API トークン）で Jira Cloud に認証する。従来の API トークンとスコープ付き API トークンの両方に対応する。README では、スコープ付きの読み取り専用トークンを使うよう案内する。
- **FR-17** 認証情報はユーザー設定ファイルに保存する。エージェントがこのファイルを読める場合もあるが、その影響は読み取り専用のトークンスコープで限定する。
- **FR-18** 認証情報は、コマンドの出力、エラーメッセージ、作業ログのどこにも現れない。

### F8. エージェントに使いやすいインターフェース

- **FR-19** 出力はエージェントが確実に解析できる構造化された形式とし、形式のバージョンを示す。バージョンを変えずにフィールドの名前を変えたり削除したりはしない。人間向けの別の表示形式は用意しない。
- **FR-20** エラーは、何が起きたか、どう直せばよいかを示し、種類（認証、許可されていないプロジェクト、見つからない、ネットワーク、タイムアウト、レート制限）を区別して、それぞれ異なる終了コードを返す。
- **FR-21** ツールは、エージェントが読める組み込みのヘルプで、自身のコマンドとオプションを説明する。
- **FR-22** jira-cli には、Claude Code にいつ、どう使うかを教える使い方ガイド（例：CLAUDE.md の抜粋や Claude Code のスキル）を同梱する。

### F9. セットアップ診断

- **FR-23** 診断チェックで、設定が揃っているか、認証情報が有効か（期限切れのトークンを含む）、Jira に到達できるか、許可プロジェクトのそれぞれにアクセスできるかを報告し、失敗ごとに直し方を示す。

### F10. 作業ログ

- **FR-24** すべての実行を記録する：日時、コマンドと引数、触れたチケット、結果（成功、またはエラーの種類）、所要時間。取得した内容そのものは記録しない。
- **FR-25** 関連チケットの取得機能を使い、別のチケット（親、サブタスク、子、リンク）からたどってチケットを取得した場合、ログには必ず起点のチケットのキーを記録する。キーを指定して直接読んだチケット、変更履歴、添付ファイルは、起点のキーなしの直接アクセスとして記録する。
- **FR-26** ログはローカルマシンにだけ保存する。コンテナを作り直したときにログが失われるのは許容する。

## 5. 非機能要件

- **NFR-1 応答性。** チケット、一覧、添付ファイルの取得は、ブラウザで同じことをするのと同程度に感じられること。厳密な目標値は設けない。
- **NFR-2 タイムアウト。** Jira への各リクエストは 30 秒でタイムアウトし、タイムアウトのエラーとして報告する（FR-20）。添付ファイルのダウンロードは代わりに、応答を 30 秒待っても来ない場合、または 30 秒間進まない場合にタイムアウトし、全体の時間には上限を設けない。
- **NFR-3 プラットフォーム。** Windows と Linux で動き、WSL や Docker コンテナの中でも動く。x64 と arm64 の両方に対応する。
- **NFR-4 構造による安全性。** 読み取り専用の動作（FR-15）と許可プロジェクトの制限（FR-12〜FR-14）は、トークンのスコープとは関係なくツール自身が強制し、自動テストで確認する。これは設計上の保証であり、利用状況の指標としては追跡しない。
- **NFR-5 レート制限。** jira-cli はステートレスで、v1 ではクライアント側の流量制御をしない。Jira がレート制限でリクエストを拒否した場合は、独立したエラーとして報告し、Jira が待ち時間を返していればそれも含める。自動の再試行はしない。
- **NFR-6 保守性。** 部内のどのエンジニアでも機能を追加できる。仕様はコードの隣で BMad メソッドを使って管理し、開発はテストファーストで行い、将来の Confluence クライアントと共有する部分は Jira 固有の部分から分けておく。
- **NFR-7 導入のしやすさ。** セットアップ時間の具体的な目標は設けない。README と診断チェック（FR-23）で十分とする。

## 6. 成功の指標

- **エージェントの円滑な利用。** Claude Code がループの Jira の手順を自力で完了し、エンジニアがブラウザからチケットの内容をコピーしなくなる。
- **ループエンジニアリングの高速化。** エンジニアが、依頼から PR までのループが速くなり、より頻繁に回すようになったと報告する。

どちらも、ツールを使うエンジニアへの個別のアンケートで集めます。アンケートの時期と質問は後で決めます（§8 を参照）。

### 逆指標

- エンジニアがブラウザからのコピーに戻ること（データの不足や出力の質の低さの兆候）。まだブラウザからコピーしているか、どんな場合かを尋ねる質問をアンケートに含める。
- 認証情報が漏れる事故。

Jira への書き込みと許可プロジェクト外へのアクセスは、計測するのではなく設計で防ぎます（NFR-4）。

## 7. 対象外

- Jira へのあらゆる書き込み：作成、編集、コメント、担当者の設定、ステータスの遷移、作業時間の記録。
- Jira に書く原因と対策の文章を生成すること。それは Claude Code が書く。
- 保存済みのフィルタープリセット、自由な JQL 検索、類似チケットの検索（次のバージョン以降の候補）。
- チケットの種類ごとに必須のフィールドを調べること。
- 1つの設定で複数の Jira サイトに接続すること。
- Jira Server / Data Center。
- v1 での Confluence へのアクセス。Confluence クライアントが後に続けるよう、共有部分は再利用できる形にしておく。
