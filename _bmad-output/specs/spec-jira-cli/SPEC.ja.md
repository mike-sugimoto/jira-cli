# jira-cli

## なぜ作るのか（Why）

解決すべき課題です。部内のエンジニアは実装やバグ修正を Claude Code に任せていますが、Claude Code は Jira を読めないため、作業のたびにチケットやチケットの一覧をブラウザからチャットにコピーしています。Jira MCP サーバーは、会社の方針、コスト、書き込み権限の広さから使えません。jira-cli は、許可プロジェクトに限定された読み取り専用の Jira Cloud CLI です。エンジニアが自律エージェントに渡せば、エージェントが必要な情報を読み、チケットをレビュー可能なプルリクエストまで進められます。

## できること（Capabilities）

- **CAP-1** チケット一覧（FR-1〜FR-3）
  - **意図：** エージェントが、名前を指定した1つ以上の許可プロジェクトのチケットを、担当者（「自分」を含む）、ステータス、課題タイプ、優先度、スプリント、ラベルで絞り込んで一覧表示し、作業するチケットを選べる。
  - **成功条件：** `list` は、キー、課題タイプ、サマリー、ステータス、優先度、担当者、最終更新日時を持つ項目を、ページ件数以内で返す。ステータスの指定が無ければ未解決（`statusCategory != Done`）のものだけを、更新日時の新しい順に返し、次ページ用の不透明なカーソルを付ける。プロジェクトの指定が無い場合、または複数の指定のうち1つでも許可外の場合は、HTTP を1本も送らずにリクエスト全体を終了コード 5 で拒否し、ヒントに許可プロジェクトのキーを示す。`maxPageSize` を超える件数の指定は終了コード 2 になる。
- **CAP-2** チケットの全体情報（FR-4〜FR-6）
  - **意図：** エージェントが、種類を問わず1つのチケットを、実装に必要な情報をすべて含めて読める。
  - **成功条件：** `get <key>` は、サマリー、説明、課題タイプ、ステータス、優先度、ラベル、コンポーネント、修正バージョン、報告者、担当者、作成日時と更新日時、古い順のすべてのコメントを返す。説明とコメントは、見出し、リスト、コードブロック、表、リンク、メンションを保った Markdown になる。値のあるカスタムフィールドは、スキーマの型に従って表示した順序付きの `[{ name, value }]` として出力する。それ以外の型は、`customFieldPassthrough` に指定したフィールドを除いて省略する。出力に関連チケットの情報は含めない。
- **CAP-3** 関連チケット（FR-7、FR-8、FR-13）
  - **意図：** エージェントが、要求に応じて1階層ずつ、任意のチケットの親、子（サブタスクとエピック配下のチケット）、リンクしたチケットを取得できる。
  - **成功条件：** `related <key>` は、各関連をキーと関係の組ごとに1回だけ、リンクの種類とともに一覧表示する。許可プロジェクト外の関連は、キーだけを `accessible: false` として示す。許可外の子のプロジェクトごとに、エンジニアに追加を依頼する通知を1つ加え、それでもコマンドは終了コード 0 で終わる。`related <origin> --key <k>` は、`k` が許可されていて、かつ本当に関連している場合だけ `k` の全内容を返し、そうでなければ終了コード 5 または 6 になる。
- **CAP-4** 添付ファイル（FR-9、FR-10）
  - **意図：** エージェントが、チケットの添付ファイルを一覧表示し、選んだもの、またはすべてをダウンロードできる。
  - **成功条件：** `attachments list` は、ファイル名、サイズ、種類、作成者、日時を表示する。`attachments download` は、`--name` 指定、チケットの添付と照合した `--id` 指定、または全件で、ツールが管理するチケットごとのフォルダに保存する。既存のファイルは置き換え、各ファイルの絶対パスを `downloaded` または `failed` として報告する。全件ダウンロードで同名のファイルがある場合は、最新のものだけを保存する。名前があいまいな場合は終了コード 2 で候補を列挙する。他の場所に書き込むオプションは無い。
- **CAP-5** 変更履歴（FR-11）
  - **意図：** エージェントが、誰が、どのフィールドを、何から何に、いつ変更したかを見られる。
  - **成功条件：** `history <key>` は、全ページのすべての変更を返す。変更前と変更後の値は、許可リストにある標準フィールドと、表示可能なカスタムフィールドの場合だけ表示する。関連のフィールドはキーで表示する。それ以外のフィールドは、フィールド名と日時だけを表示する。
- **CAP-6** アクセス制御（FR-12〜FR-15、NFR-4）
  - **意図：** トークンの権限とは関係なく、jira-cli 自身が読み取り専用と許可プロジェクトを強制する。
  - **成功条件：** Windows と Linux の自動テストで、次のことを証明する。GET しか送らないこと。他プロジェクトのチケット、移動済みチケット、一覧の結果、子、埋め込まれたデータからは一切内容が出ないこと。どのオプションや環境変数でも、設定ファイルのパスや許可プロジェクトを変えられないこと（悪意ある `HOME`、`XDG_*`、`USERPROFILE`、`APPDATA`、`LOCALAPPDATA` を含む）。
- **CAP-7** 認証（FR-16〜FR-18）
  - **意図：** jira-cli は、エンジニア自身のメールアドレスと API トークン（従来型またはスコープ付き）で認証し、トークンを決して露出させない。
  - **成功条件：** サイトの URL 経由の従来型トークンと、`cloudId` のゲートウェイ経由のスコープ付きトークンの両方で認証でき、認証情報はそのベース URL にしか送られない。401 と 403 は終了コード 4 になり、ヒントで期限切れ、スコープ不足、`cloudId` に触れる。テストでは、仕込んだトークンが stdout、stderr、ログのどこにも、`@file` 引数経由でも現れない。
- **CAP-8** エージェントに使いやすいインターフェース（FR-19〜FR-22）
  - **意図：** エージェントが、すべての結果を確実に解析し、エラーの種類を見分け、ヘルプと同梱の使い方ガイドからツールの使い方を学べる。
  - **成功条件：** すべての実行で、`formatVersion` を含む JSON のエンベロープを1つだけ stdout に書く。プレーンテキストを出すのは `--help` と `--version` だけ。エラーの種類は 0〜10 の固定の終了コードに対応し、レート制限による拒否は終了コード 9 で、Jira が返していれば `retryAfterSeconds` を含める。各コマンドの出力はゴールデンテストで固定する。`--help` はすべてのコマンドとオプションを説明する。使い方ガイドはパッケージに同梱し、AD-22 が挙げる内容を扱う。
- **CAP-9** セットアップ診断（FR-23）
  - **意図：** エンジニアが1つのチェックを実行すると、セットアップの何が問題で、どう直せばよいかが分かる。
  - **成功条件：** `doctor` は、設定が揃っているか、認証情報が有効か（期限切れのトークンを含む）、Jira に到達できるか、許可プロジェクトのそれぞれにアクセスできるか、使用中のエンドポイントを報告し、失敗ごとに直し方を示す。設定が不正な場合でも実行できる。
- **CAP-10** 作業ログ（FR-24〜FR-26）
  - **意図：** すべての実行が、内容を含めずに、何にアクセスしたかの記録をローカルに残す。
  - **成功条件：** `--help` と `--version` を除くすべての実行で、日時、コマンド、マスキング済みの引数、触れたチケット、起点、結果の種類、所要時間を含む JSON の1行を、ローカルの UTC 日付別ファイルに追記する。レスポンスの内容は記録しない。`related <origin> --key <k>` は起点を記録する。ログの書き込みに失敗した場合は stderr に警告を出すだけで、stdout と終了コードは変わらない。
- **CAP-11** インストールとセットアップ（NFR-3、NFR-7、FR-12、FR-16）
  - **意図：** エンジニアが、README だけを頼りに、WSL、Docker、Windows で jira-cli をインストール、設定、保護できる。
  - **成功条件：** 1つの `.nupkg` を `dotnet tool install -g jira-cli --source <folder>` でインストールでき、Windows と Linux の x64 と arm64 で動く。README は、AD-22 が挙げるすべての内容に加え、設定ファイルの場所とすべての設定項目、プロキシ、ルート証明書を扱う。README に従った後は `doctor` が成功する。

## 制約（Constraints）

- アーキテクチャは採用したスパインに従う。Clean Architecture 風のプロジェクト分割の上にヘキサゴナルを置き、AD-1〜AD-22 がすべての作業を縛る。
- 型で読み取り専用にする：transport は GET しか送れない（FR-15、AD-5）。
- Jira への呼び出しはすべて `JiraGateway` を通り、呼び出しの前後でプロジェクトへのアクセスを確認する（AD-4、AD-7）。
- 設定ファイルのパスは固定で、OS のユーザー情報から解決し、環境変数やオプションは決して使わない（FR-14、AD-11）。
- 認証情報は、出力、エラー、ログのどこにも現れない（FR-18、AD-12）。
- .NET 10 の C# で、Windows と Linux、x64 と arm64、WSL と Docker を含めて動く（NFR-3）。
- 標準の .NET DI と、interface ベースで注入可能なサービスを使う。テストファーストで、テストは実際の Jira を呼ばない（NFR-6、AD-20）。
- `Atlassian.Common` は Jira の概念を持たず、Confluence クライアントが再利用できるようにする（NFR-6、AD-2）。
- Jira Cloud REST API v3 だけを使い、1つの設定で接続するサイトは1つ。
- ステートレス：クライアント側の流量制御も、自動の再試行もしない（NFR-5）。
- JSON のリクエストは 30 秒でタイムアウトする。添付ファイルのダウンロードは、応答を 30 秒待っても来ない場合、または 30 秒間進まない場合にタイムアウトする（NFR-2、AD-19）。
- 共有フォルダのソースから、フレームワーク依存の .NET ツール1つとして配布する。すべての環境に .NET 10 SDK がある。社内 NuGet サーバーは無い（AD-21）。
- 1つのインストールを使うエンジニアは1人で、社内ツールであり、エージェントは root で動かない。

## 対象外（Non-goals）

- Jira へのあらゆる書き込み：作成、編集、コメント、担当者の設定、ステータスの遷移、作業時間の記録。
- Jira に書く原因と対策の文章を生成すること。それは Claude Code が書く。
- 保存済みのフィルタープリセット、自由な JQL、類似チケットの検索。
- チケットの種類ごとに必須のフィールドを調べること。
- 1つの設定で複数の Jira サイトに接続すること。Jira Server と Data Center。
- v1 での Confluence へのアクセス。
- 人間向けの表示形式。
- 呼び出し側が選んだフォルダへの添付ファイルのダウンロード。
- トークンを読んで別の手段で Jira を呼ぶエージェントや、プロセスの環境、Windows のレジストリ、ダウンロード中の管理フォルダを変更するエージェントを止めること（AD-3）。
- 設定ファイルが書き込み可能かどうかを実行時に確認すること。
- 応答性の厳密な目標値。取得はブラウザと同程度に感じられればよい（NFR-1）。

## 成功の兆し（Success signal）

- 部内の Jira サイトで、エンジニアが Claude Code にプロジェクトの未解決チケットの一覧を頼み、その1つの作業を任せる。Claude Code はループの手順 1、2、5 を、ブラウザからのコピーなしに jira-cli で完了し、AD-20 の安全性テストが Windows と Linux で通る。
- アンケートで、エンジニアが、依頼から PR までのループが速くなり、より頻繁に回すようになり、ブラウザからのコピーに戻らなくなったと報告する。認証情報の漏洩は起きない。

## 未解決の質問（Open Questions）

- Jira の実際の動作は公開された仕様どおりか：Basic 認証での `redirect=false`、スコープ付きトークンでの添付ファイルへのアクセス、プロジェクトをまたぐ `parent =`、`expand=schema` の型名、コメントの `total`、`statusCategory` での絞り込み。最初の Gateway と添付ファイルのストーリーで判断する。
- エージェントの環境から書き込めない共有フォルダのソースをどこに置き、どの CI でリリース前のテストを実行するか。部内への展開前に決める。
- アンケートの時期、基準値、質問をどうするか。担当：Mike。部内への展開前に決める。
